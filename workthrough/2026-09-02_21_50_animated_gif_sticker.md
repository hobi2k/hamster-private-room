# 움직이는 GIF 스티커와 GIF 내보내기 연결

## 개요
GIF 파일을 스티커처럼 붙여 위치·크기·투명도를 조절하고, 글과 함께 움직이는 GIF로 저장하는 기능을 완성했다. 이전 커밋에서 GIF 인코딩 파이프라인(`animatedGif.ts`)은 이미 있었지만 업로드 단계에서 애니메이션이 사라져 동작하지 않는 상태였다.

## 주요 변경사항
- 고친 것: `imageFileToDataUrl`이 모든 업로드를 캔버스로 다시 그려 WebP로 저장하면서 GIF의 첫 프레임만 남기던 문제. GIF는 원본 바이트를 그대로 데이터 URL로 보존하도록 분기했다. 이 때문에 `isGifSource`가 한 번도 일치하지 않아 GIF 내보내기가 항상 `NO_ANIMATED_GIF`로 실패했다.
- 개발한 것: `src/lib/gif.ts` — GIF 시그니처 판별, 블록 스트림을 걸어 프레임 수·재생 시간·화면 크기를 읽는 파서, 청크 단위 base64 인코딩, 저장 용량 경고/거부 기준
- 개발한 것: `src/lib/sticker.ts` — 스티커 크기·투명도 정규화와 가로세로 비율 상자 계산, 예전 문서 마이그레이션
- 개발한 것: 스티커 투명도 조절 슬라이더. `StickerLayer`에 `opacity`가 아예 없었다.
- 개선한 것: 스티커가 항상 정사각형(`size` × `size`)이라 정사각형이 아닌 GIF가 찌그러져 보이던 상자를 `size`를 긴 변으로 삼아 비율을 지키도록 변경
- 개선한 것: 스티커 최대 크기를 220px에서 480px로 확대(패널 슬라이더·드래그 손잡이·문서 로딩 clamp 일치)
- 개선한 것: 팔레트 썸네일의 GIF 배지, 선택 스티커의 "움직이는 GIF" 표시, 프레임 수를 알려주는 안내 토스트
- 개선한 것: 프레임이 1장인 GIF는 움직이지 않는다고 안내하고, 내보내기도 `NO_ANIMATED_GIF`로 처리해 한 장짜리 "애니메이션"을 만들지 않도록 방어
- 검증한 것: GIF 파서·크기 경고·비율 상자·투명도 마이그레이션 자동 테스트 22개 추가

- ✅ 프로덕션 빌드 통과

- ✅ 브라우저 오류 로그 없음

## 후속 수정 — 재생 속도 정확도

사용자 피드백: "저장은 되지만 원본 프레임보다 느려진다."

- 원인: 페이지를 고정 125ms 격자로 샘플링하고 모든 출력 프레임에 125ms를 박아 넣었다. 12×100ms(1200ms) GIF는 10프레임/1250ms(+4.2%)가 되면서 원본 4·9번 프레임이 통째로 사라졌고, 불균등 delay GIF는 +10.3%까지 느려졌다.
- 고친 것: 고정 격자를 버리고 원본 GIF들의 프레임 경계 합집합을 타임라인으로 쓰고, 각 출력 프레임에 원본의 실제 delay를 기록한다. GIF는 delay를 센티초로 저장하고 gifuct가 주는 delay는 항상 10ms 배수, gifenc는 `Math.round(delay/10)`으로 변환하므로 왕복이 무손실이다.
- 방어한 것: 클립이 여러 개일 때 주기의 최소공배수가 가장 긴 클립의 2배를 넘으면 가장 긴 클립 주기로 자른다. 1020ms와 1200ms는 20.4초(약 150캡처, 3분)를 요구했는데 이제 1200ms/19프레임/20초로 끝난다. 각 클립의 재생 속도는 그대로 정확하다.
- 상한 변경: 재생 시간 5초 상한을 프레임 수 80개 상한으로 교체했다. 프레임당 페이지 캡처가 약 1초라 이게 곧 내보내기 시간 상한이다.
- 알린 것: 완료 토스트에 프레임 수·총 길이와 원본 속도 일치 여부를 표시한다.

## 후속 결과
- ✅ Vitest 104개 통과 (타임라인 10개)
- ✅ 헤드리스 왕복: 실제 GIF에서 delay를 뽑아 실제 gifenc로 인코딩 후 재파싱 — 12×100ms는 12프레임/1200ms, 불균등은 40,200,90,500,130,60 전부 보존
- ✅ 브라우저 실제 내보내기: 불균등 GIF가 delay 6개 그대로 1020ms, 두 클립 동시에 19프레임/1200ms/20초
- ⚠️ 색상은 여전히 프레임마다 256색 재양자화 — 페이지 전체를 GIF로 합치는 구조상 불가피
